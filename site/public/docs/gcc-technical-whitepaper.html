1.3 Two-ORM Strategy

A single Neon PostgreSQL database is shared by two application-layer ORMs, each optimized for its runtime environment. The Drizzle ORM (TypeScript) drives the Next.js API layer with type-safe query building and is the schema source of truth — all migrations originate from Drizzle's schema definitions. The Exposed ORM (Kotlin) maps those same tables for Ktor's server-side business logic using a JDBC connection configured with stringtype=unspecified to bridge Exposed's varchar handling with PostgreSQL's native enum types.

Drizzle ORM (TypeScript)

  • Schema source of truth
  • Flat columns + native PG enums
  • Runs in Vercel serverless functions
  • Connection via Neon serverless driver
  • Migration files committed to VCS

Exposed ORM (Kotlin)

  • Maps to existing Drizzle schema
  • HikariCP connection pool
  • JDBC URL with stringtype=unspecified
  • Runs on long-lived JVM process
  • No independent migrations

1.4 Kotlin Multiplatform Shared Module

The shared/ KMP module defines all domain models, API types, and enumerations in platform-agnostic Kotlin. This module compiles to:

iosArm64 / iosSimulatorArm64 Kotlin/Native framework iOS app (SwiftUI interop)
androidTarget Kotlin/JVM (Android) Android app (Jetpack Compose)

All serialization uses kotlinx.serialization with @SerialName annotations mapping to snake_case JSON keys, ensuring wire-format consistency across all platforms without manual parsing logic.

Block Cleaning 2-Lap Model

GCC's operational model is structured around a two-pass approach to street-level environmental cleanup. Physical geography is modeled through two complementary views of the same road segment: Blocks (sponsorship/funding view) and Routes (worker/cleanup operational view). These maintain a strict 1:1 relationship.

2.1 Block ↔ Route Duality

Concept View Code Pattern Key Fields Geometry
Block Sponsor & funding NL-N01, NL-S01 fundingGoal, fundingCurrent, sponsorId, boundary (Polygon) GeoJSON Polygon
Route Worker & cleanup NL-RN01, NL-RS01 distanceMeters, estimatedDurationMinutes, payoutAmount, geometry (LineString) GeoJSON LineString

Code conventions: {ServiceArea}-{Direction}{Number} for blocks (e.g., NL-N01 = North Lawndale, North sector, block 1) and {ServiceArea}-R{Direction}{Number} for routes (NL-RN01 = route for NL-N01). Display images are shared between paired blocks and routes.

2.2 Lap 1 — Documentation Walk

Start Checkpoint GPS Track Along Route Photo @ Dirty Spot AI Classification GPS Tag + Severity End Checkpoint

The worker follows a predefined route (GeoJSON LineString geometry), passing through ordered checkpoints. Each checkpoint has a CheckpointType that determines the required action:

Checkpoint Type Purpose Photo Required Geofence Radius
ROUTE_STARTBegin route session, GPS lockOptional15m default
PHOTO_POINTMandatory documentation pointYes15m default
ALLEY_ENTRANCEMark alley access pointYes15m default
RECORDDocument conditions (Lap 1)Yes15m default
CLEANPerform cleanup (Lap 2)Yes (before/after)15m default
VERIFYVerify previous reportYes15m default
RECORD_CLEAN_VERIFYCombined multi-action checkpointYes15m default
ROUTE_ENDComplete route sessionOptional15m default

At each dirty spot encountered during the documentation walk, the worker captures a photo which triggers the on-device AI pipeline. The LiDAR variant (iPhone Pro models) adds depth analysis for precise volume estimation of debris piles. All captures include a device attestation record binding the photo to a specific GPS coordinate, timestamp, and device fingerprint.

2.3 Lap 2 — Cleanup Pass

Return to Spot Before Photo Start Cleanup Timer Bag & Categorize After Photo Submit Report

The cleanup pass returns to each documented spot. The mobile app tracks:

  • Before/after photo pairs — stored as beforeMediaUrls / afterMediaUrls
  • Cleanup timer — startedAt to completedAt, cancellable coroutine Job
  • Trash heap documentation — separate photo of collected bags (trashHeapMediaUrl)
  • AI analysis of collected waste — aiTrashAnalysis on heap photo
  • GPS verification — locationVerified against original spot coordinates

Verification System

The verification system ensures data integrity by requiring independent community confirmation of reported conditions. It implements a 24-hour re-verification cycle, GPS proximity enforcement, and anti-gaming protections.

6.1 Verification Protocol

Constraints

  • 24-Hour Cycle — Every spot requires re-verification within 24 hours of creation or last verification
  • GPS Proximity — Verifier must be within 200 meters of the spot (Haversine distance)
  • Self-Verification Block — Original reporter cannot verify their own spot
  • Photo Evidence — All verifications require a current photo

Concurrency Control

  • Optimistic Concurrency — expectedVerificationCount prevents race conditions
  • Atomic Update — Verification count + status change in single transaction
  • Conflict Resolution — First-write-wins; concurrent submitters receive conflict error

6.2 Verification Record

data class SpotVerification(
    val id: Int,
    val reportId: Int,                     // FK to community_reports
    val verifierId: Int,                   // FK to workers
    val verifierName: String?,
    val result: SpotVerificationResult,    // STILL_DIRTY | ALREADY_CLEAN
    val photoUrl: String?,                 // Required verification photo
    val verifierLat: Double?,              // GPS at verification time
    val verifierLng: Double?,
    val distanceFromSpotMeters: Double?,  // Computed Haversine distance
    val pointsAwarded: Int,               // 5 (dirty) or 10 (clean)
    val createdAt: Instant,
)

6.3 Verification Outcomes

Result Spot Effect Points Side Effects
STILL_DIRTY Spot remains open; next_verification_due reset to +24h 5 Verification count incremented; escalation if repeated
ALREADY_CLEAN Spot status → resolved; resolved_at set 10 Cleanup credit; linked bounties fulfilled; spot closed

6.4 Escalation Path

If a spot's next_verification_due timestamp expires without a new verification, the system flags it for admin notification. Spots verified as STILL_DIRTY three or more times are escalated for priority cleanup scheduling. The needsVerification boolean field provides a quick filter for the mobile app's "nearby verifications needed" feature.

11.3 Cleanliness Score Algorithm

The cleanliness score is a composite metric computed identically in both TypeScript (website) and Kotlin (server) to ensure consistency. It uses three individually-capped penalties to prevent any single factor from dominating: 

// Canonical implementation (TypeScript + Kotlin, kept in sync)
function computeCleanlinessScore(
    activeSpots: number,       // Currently open spot reports in area
    avgDurationHours: number,  // Average time spots stay open
    recurrenceRate: number,    // Rate of spots reappearing (0.0-1.0)
): number {
    const activePenalty    = Math.min(40, activeSpots * 3)
    const durationPenalty  = Math.min(30, avgDurationHours / 4)
    const recurrencePenalty = Math.min(30, recurrenceRate * 100)
    return Math.max(0, Math.min(100,
        Math.round(100 - activePenalty - durationPenalty - recurrencePenalty)
    ))
}

GCC's architecture is designed for progressive geographic expansion from a single pilot neighborhood to city-wide coverage and beyond. The service area model provides the fundamental unit of geographic scaling.

13.2 Service Area Model

// ServiceArea — unit of geographic scaling
data class ServiceArea(
    val id: Int,
    val name: String,                     // "North Lawndale"
    val city: String,                     // "Chicago" (default)
    val state: String,                    // "IL" (default)
    val boundary: GeoJSONPolygon?,        // Geographic boundary
    val mapCenter: Coordinates?,          // [lng, lat] center point
    val mapZoom: Double,                  // Default map zoom level
    val status: ServiceAreaStatus,        // PLANNING | PILOT | ACTIVE | PAUSED
    val totalBlocks: Int,                // Number of blocks in area
    val activeWorkers: Int,              // Workers assigned to area
)

13.4 Multi-City Readiness

The architecture supports expansion beyond Chicago through several design decisions:

  • Geographic abstraction — Service areas, blocks, and routes are not Chicago-specific; any city with geographic subdivisions can be modeled
  • GeoJSON standard — All geographic data uses GeoJSON format ([lng, lat] coordinate order) for universal compatibility
  • Configurable taxonomy — Community area numbers, wards, police districts, and census tracts are stored as generic fields that can map to any city's administrative boundaries
  • Per-area isolation — Each service area has its own boundary, blocks, routes, workers, cleanliness tracking, and analytics
  • SODA compatibility — The export API follows open data conventions used by hundreds of municipal data portals nationwide
